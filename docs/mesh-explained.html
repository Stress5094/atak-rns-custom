ATAK over Reticulum / LoRa

How the mesh works

Every ATAK device on the network shares one radio channel with no internet, no phone signal and no server. This is what goes over that channel, and every rule that decides what gets to.

The one thing that explains everything else

There is a single radio channel. Only one node can talk at a time, and nobody can hear while transmitting. On the fastest setting the whole network moves about 21 kilobits per second — roughly a thousandth of a home Wi-Fi link. On the default setting it is twenty times slower again.

So the scarce resource is not bandwidth, it is time on the air. Nearly every design decision below exists to avoid spending it. When you see a rule that looks fussy, it is almost always buying airtime back.

Measured Push acknowledged messages onto four real nodes and it carries 80 a minute perfectly and delivers almost nothing at 120. Beyond that the channel jams and stays jammed. That is the budget everything here is spending.

Sending: five gates, in order

Nothing goes on the air without passing all five. Most things never reach the end.

  1. Should this be sent at all?

    The single biggest airtime saving in the system

    ATAK emits position updates constantly. Sending them all would flood the channel, so each one is judged on whether it actually tells anyone anything new.

    • Sent immediately — a person the network hasn't seen before; a changed callsign, team or role; and the first move after standing still, which is the most informative report there is and is never delayed.
    • Sent at a limit — someone who keeps moving is capped at one report a minute. Someone standing still sends one a minute as a heartbeat.
    • Dropped — moves under 25 metres; anything with no GPS fix; ATAK's own keepalive chatter; chat read-receipts; and anything the app itself put into ATAK moments ago, which would otherwise loop around the network forever.

    Chat, markers, drawings and routes skip this gate entirely. A person pressed send, so it goes.

  2. Make it as small as possible

    ATAK speaks XML, which is enormously wasteful on a radio this slow. A position report arrives as about 800 bytes of text and leaves as roughly 60 — the app knows the shape of every event type and rebuilds it on the far side rather than sending the words. Chat, markers, shapes, circles and routes each have their own compact form. Whatever is left is then squeezed against a dictionary trained on real ATAK traffic, and the smaller of the two results wins.

  3. Will it fit in one transmission?

    If not it is cut into numbered slices, up to sixteen. The receiver holds the pieces until the set is complete. This is why a long route costs so much more than a chat message — and why, when one slice goes missing, only that slice is asked for again rather than the whole thing.

  4. Does it need proof it arrived?

    Positions do not: another one is along shortly and replaces it. Chat, markers, drawings and routes do — there is no later event to supersede a lost one, and a message that silently vanishes is the worst failure this system can have. Those get wrapped as needing an answer.

  5. Seal it

    Everything is encrypted and stamped before transmission, under a key derived from a passphrase every node shares. The seal costs 16 bytes and carries who sent it, a key generation number, and a counter — which is also how the network recognises a message it has already seen.

Receiving

The same steps, backwards, with two extra jobs in the middle.

The envelope is opened first. If it will not open, the frame is from a node with a different passphrase and is discarded — it is not on this network. If it opens but has been seen before, it is dropped as a duplicate, which is what stops a relayed message circulating forever.

Then, before anything is decoded, the node decides whether to pass it on. Only after that are fragments reassembled, the compact form expanded back into XML, and the result handed to ATAK, which draws it on the map as though it came from a server.

Relaying, and why it usually does nothing

Every node repeats what it hears — but only when repeating would actually reach somebody the sender could not. This is the rule that keeps a mesh from drowning itself.

Each beacon carries a compact summary of who that node can hear. When a message arrives, the receiver compares the sender's list against its own. If the sender already reaches everyone the receiver reaches, repeating it is pure waste and it stays quiet.

Three further limits sit on top of it:

  • A hop budget per kind. Beacons are never repeated at all — they are what defines who is next to whom, and flooding them would make everyone look adjacent and destroy the test above. Positions get two hops, chat and drawings three.
  • An airtime allowance. Each node may spend about 1.5 seconds a minute relaying. Past that it refuses, so relaying can never itself be the thing that jams the channel.
  • The weakest signal goes first. Nodes that might relay the same message wait a moment before doing it, and the one that heard it faintest waits least — it is furthest away and most likely to be the one that actually extends reach. Anyone who hears somebody else do it first stays quiet.

Making sure a message arrived

Only chat, markers, drawings and routes are tracked. When one is sent, the app notes who was present and expects an answer.

One answer is enough. An early version had every listener reply, which cost one acknowledgement per person on the network. Now the sender says a single reply will do, everyone waits a random fraction of a second, and whoever goes first silences the rest. A chat addressed to one specific person is different: only that person may answer, because a bystander's reply would report the message delivered when the recipient never saw it.

If no answer comes, the message is sent again — up to four attempts, spaced further apart each time. If pieces are missing rather than the whole thing, only the missing pieces go. After the fourth attempt the sender is told plainly that it did not arrive, on screen and in the log.

Newest, and not yet tested on real radios

Retrying stops when the channel is full. Repeating a lost message needs airtime on a channel that has already run out, so more is lost, so more is repeated — which is exactly how a busy network becomes a dead one. Testing showed that past the limit this machinery spent about seventy percent of the channel to deliver nothing whatsoever.

So retries now pause when more than four messages are waiting at once. That number is not a guess: on real hardware every load the network handled perfectly had one message waiting, and every load that failed had twenty or more. Because pausing means a message can no longer run out of attempts, each one also carries a deadline, so it ends honestly instead of hanging forever.

Knowing who is out there

Every node announces itself once a minute, and that announcement carries the list of who it can hear. It is skipped if the node has transmitted recently anyway — no point proving a link that just proved itself — but it is never left longer than ninety seconds, because that list is what every other node's relay decision depends on.

Someone is considered present for three minutes after their last transmission. That is deliberately generous: a node behind a wall for a moment should not vanish from the map. People who genuinely leave are kept on the list far longer, greyed out, because “who dropped off?” is the question you actually want answered.

Who can read it

One passphrase, shared by everyone on the network. Holding it is what makes you a member — a node that cannot decrypt is not a peer and its beacons are ignored. Every transmission is encrypted and tamper-checked, so an outsider on the same frequency hears noise and cannot inject anything.

Stated plainly, because it is a real limit: this authenticates the group, not the individual. Anyone holding the passphrase can claim to be any node on the network. That is the same trade Wi-Fi passwords make, and it suits a squad whose radios are all accounted for — but a lost radio compromises the group until the passphrase is changed. There is deliberately no default passphrase; a new node generates one and stays alone until you share it.

The app shows a four-character fingerprint of the key, so two devices can be checked at a glance. This matters more than it sounds: a wrong passphrase and a dead radio look identical from the outside.

How far, versus how fast

Eight radio settings, chosen in the app and matched across every device. They trade range against speed, and the span is enormous — the fastest is about a hundred and twenty times the throughput of the slowest, and a fraction of the range. Everything measured in this document was on the fastest setting; the default is twenty times slower, and every airtime figure scales accordingly.

The honest limits

Four nodes on a desk, on the fastest radio setting, delivering perfectly up to 80 messages a minute and failing completely at 120. Collapse is abrupt, not gradual, and it does not recover on its own — messages caught in it are lost, not delayed.

Two things that have never been tested: the movement rules, because that needs somebody walking with a GPS fix rather than phones on a bench; and the new retry-pausing, which is built from these measurements but has not yet been on a radio.

Making the small messages small

Most of what this radio sends is tiny — a "still here" ping, or a "got it" receipt. Every message also carries a fixed address label and security seal, and measuring them side by side turned up something awkward: on the messages we send most often, the label and seal were about two thirds of what went out. Years of effort had gone into shrinking the messages themselves, which by then were the small part.

So this round shrank the wrapping instead. Names are written the short way, anything the sealed envelope already proves is no longer repeated inside it, and the seal itself is half the size. A "got it" receipt went from 17 bytes to 6. Several small messages can now also share one envelope, which is worth more than it sounds: four receipts sent together take 60 bytes instead of 148.

The bigger change is that phones no longer need to speak up every minute. They used to, for one reason: ATAK removes a marker from the map if it has not heard about it in roughly two minutes. So the radio was keeping a countdown in somebody else's software happy. Now the receiving phone simply keeps the marker longer, and this bridge takes it off the map itself when it notices that node has gone quiet — which it was already tracking anyway.

Sixteen phones standing still used to spend 6.3% of the radio doing nothing but resetting each other's timers. That is now 3.1%.

What it costs, plainly

A dead radio now takes 3–4½ minutes to disappear from the map instead of 1–2. That is the trade, and it is the one to argue with.

It is less bad than it sounds, because the old fast answer was also an unreliable one. Giving up after two minutes when phones check in every minute means giving up after roughly one missed message. Every test so far has been with the radios sitting inches apart, where nothing is ever lost — out at real range, every dropped packet would have blinked a perfectly healthy marker off the map and back. Waiting for a run of missed check-ins is slower but stops crying wolf.

The seal being half its old size is also a genuine, deliberate weakening. It is still far beyond anyone's reach at this radio's speed, and it was never the weakest part of the design — sharing one password across the whole group is.

None of this has been on a radio yet, and one step in particular is an assumption rather than a measurement: that ATAK really does remove a marker when told, after the fact, that it has expired.

How this compares to Meshtastic, Reticulum and MeshCore

Assume all four are running the same fastest radio setting. Then none of them is faster than the others, because they are all limited by the same 21,875 bits per second and the same one-at-a-time channel. That ceiling is physics, not software.

So the real question is not who is quicker. It is what each one spends that ceiling on, and what you get back for the spending.

Throughput — we are probably last

Our overhead is the worst of the four and it is not close: 12 bytes for our own seal plus 19 more for Reticulum's packet header, against Meshtastic's 16 in total. Add an acknowledgement costing half a message, and a protocol that makes no promises will carry more messages a minute on the same radio than we do. If your only measure is raw messages delivered, we lose.

Reliability — strong, but deliberately narrow

We are the only one of the four that will state plainly that a specific message did not arrive, and the only one that re-sends just the missing slice of a split message rather than the whole thing. Reticulum's own machinery is stronger than ours — we choose not to use it, because addressing each recipient individually costs more channel than exists at squad size. Meshtastic broadcasts carry no delivery guarantee at all.

Corrected 2026-08-17

The table above used to credit MeshCore with a flat yes on this. That was too generous, and the distinction is the one that matters for a map. MeshCore confirms delivery for messages sent to one named person. Messages to a group or channel get no confirmation at all — they are decrypted, passed on, and nobody answers.

Everything a shared map is made of — positions, markers, drawings — is a message to the whole group. So on the traffic this project actually carries, MeshCore is in the same position as Meshtastic: silence. Confirming a message sent to everybody is a harder problem than confirming one sent to a single node, and it is the one we solved. That is why our confirmation costs more than their four bytes.

Scale — three different bets

The four projects answer “who repeats this?” in genuinely different ways, and each answer suits a different shape of network.

  • Meshtastic repeats everything, everywhere. Simple and hard to break, but at one position a minute per node it wants roughly twice the channel that exists.
  • MeshCore floods once to find a route, then sends along it. The packet carries the actual list of nodes to pass through — one byte per hop — so after discovery only those nodes repeat, and everyone else stays quiet. Nodes set as “companions” never repeat at all.
  • We never repeat while the group is together. The coverage test means no node speaks up unless it reaches somebody the sender could not.

The difference is what each is optimised for. MeshCore's route learning pays off when the same two people exchange many messages — you find the path once and reuse it. Ours pays off when everybody needs everything, which is what a map full of position reports actually is. Neither is better in the abstract; they are tuned for different traffic.

Read this before quoting any of the above

Only one of these four has been benchmarked here, and it is ours. The 80-messages-a-minute figure was measured on real radios. Every other row comes from reading documentation and design notes, not from running it. A fair comparison means putting each one on the same two radios and ramping it identically, which has not been done.

The MeshCore figures come from reading its source directly, so the routing and the two-byte header are solid — but its addressing and encryption live inside the message body rather than the header, so its two bytes and our thirty-five are not quite measuring the same thing, and a full like-for-like total has not been worked out. Separately, our security advantage has an expiry: Meshtastic's packet signing closes that gap in an upcoming firmware release.

The short version: we trade throughput for honesty about delivery, and per-message efficiency for a relay policy that should hold up better as the group grows. Whether that is the right trade depends on whether your squad is standing together or spread out.
